Cloud Portfolio: Application Architecture Planning and Design

July 12, 2026 · 6 min read

I started the application design with boundaries rather than technologies. Content areas have different change patterns, while the contact form has runtime logic and secrets. That led to four static Nginx services and one Node.js service.

Service boundaries

  • Portfolio service: homepage, contact page, and the public Nginx routing layer.
  • Experience service: career timeline and dynamic total-experience display.
  • Projects service: project case studies and links to related technical writing.
  • Blog service: article index and independent article subpages.
  • Contact service: validation, rate limiting, HTML escaping, and SES SMTP delivery.

Request flow

Browser
  -> CloudFront
      -> portfolio_service:80
          +-- /experience/  -> experience_service:80
          +-- /projects/    -> projects_service:80
          +-- /blog/        -> blog_service:80
          +-- /api/contact  -> contact_service:3000

The portfolio container is the only service bound to the host's public HTTP port. Nginx rewrites the public path prefix and resolves upstream containers through Docker DNS. Forwarded headers preserve the original request context, and short proxy timeouts prevent a failing dependency from tying up connections indefinitely.

Why separate static services?

For a small portfolio, microservices are not necessary for scale. Here they are a deliberate learning and delivery choice. They demonstrate independent build and rollback boundaries and make routing behavior visible. The cost is duplicated Nginx, CSS, and JavaScript configuration; a shared design package or static-site build step would reduce that duplication later.

Security decisions

Only the gateway publishes a host port. The contact API is reached through the gateway, validates required input, limits requests, escapes submitted content, and reads SMTP configuration from runtime environment variables. Browser code never receives SMTP credentials.

Design assessment

This architecture is appropriate as a compact demonstration platform, not a universal template. If traffic, team size, or availability requirements grew, I would move state and secrets into managed services, add a load-balanced multi-host runtime, and standardize shared frontend assets. Architecture should evolve from measured needs rather than tool preference.
