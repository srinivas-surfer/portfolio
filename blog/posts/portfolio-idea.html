Cloud Portfolio: The Idea and Engineering Goals

July 12, 2026 · 4 min read

A portfolio can be a set of static pages, but I wanted mine to demonstrate how I approach reliability engineering. The idea was to make the platform itself part of the portfolio: small services, explicit infrastructure, controlled delivery, health checks, rollback, and operational reporting.

The problem I wanted to solve

A single static site would be inexpensive and easy to operate, but it would reveal little about deployment design or service ownership. A large application would add complexity without improving the visitor experience. I chose a middle path: keep the user interface simple while using the delivery platform to demonstrate practical SRE and DevOps patterns.

Engineering goals

  • Allow the homepage, experience, projects, blog, and contact API to change independently.
  • Keep only one controlled entry point public while application services remain private.
  • Represent AWS infrastructure as code so the environment is reproducible and reviewable.
  • Build immutable images and deploy them through approval-gated pipelines.
  • Make every release observable, testable, and reversible.
  • Avoid storing contact-form credentials or other secrets in the repository.

Constraints shaped the design

This is a personal platform, so cost and operational effort matter. Running a managed orchestrator would demonstrate more Kubernetes knowledge, but it would be excessive for five small services. Docker Compose on one EC2 host is an intentional tradeoff: it preserves service boundaries and independent delivery while keeping the platform understandable and affordable.

My view

The strongest portfolio projects tell a coherent engineering story. The value here is not the number of tools; it is the connection between a requirement and a decision. Independent changes led to service boundaries, safe releases led to immutable tags and rollback history, and public delivery led to CloudFront with a single Nginx origin gateway.
