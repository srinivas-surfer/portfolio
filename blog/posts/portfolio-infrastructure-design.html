Cloud Portfolio: Infrastructure Planning and Design

July 12, 2026 · 6 min read

The infrastructure plan optimized for three things: a small operational footprint, controlled public access, and enough automation to recreate and review the environment. Terraform provisions the AWS foundation, while Docker Compose defines the application runtime.

AWS foundation

The Terraform configuration creates a dedicated VPC, public subnet, internet gateway, route table, security group, and EC2 host. SSH source ranges and allowed HTTP origin ranges are variables rather than hard-coded universal access. EC2 user data installs and prepares the container runtime.

Edge and origin design

Route 53 -> CloudFront -> EC2:80 -> Nginx gateway -> private services

Route 53 provides DNS and CloudFront is the public delivery layer. CloudFront should terminate TLS with an ACM certificate, cache static routes, and avoid caching the contact API. The EC2 security group can restrict origin HTTP access to approved ranges instead of treating the host as the primary public edge.

Runtime and deployment

Docker Compose places all services on one explicitly named network. Only the portfolio service publishes port 80; the remaining services use internal ports. GitHub Actions builds immutable Git-SHA images, validates them, and deploys a selected service with --no-deps so unrelated containers are not restarted.

Recovery planning

Deployment history records verified image tags and retains the previous release locally. Operators can roll back to an explicit tag or N-1 image through a protected manual workflow. Smoke tests verify public routes after change, and recovery documentation makes the process repeatable.

Tradeoffs and next design

A single EC2 instance is cost-effective but remains a failure domain. For higher availability, I would place workloads across multiple instances or a managed container service behind an Application Load Balancer, move secrets to AWS Secrets Manager or Systems Manager Parameter Store, centralize logs, and add tested backup/restore procedures. I would make that move only when the availability objective justifies its cost and complexity.

Final thought

Infrastructure design is strongest when every component answers a requirement. Terraform answers reproducibility, CloudFront answers public delivery and caching, private Docker networking limits exposure, immutable tags support traceability, and rollback history supports recovery. That chain of reasoning is more valuable than adding services without an operational purpose.
