AI-Assisted Anomaly Detection for E-commerce Orders

July 12, 2026 · 8 min read

Hourly order traffic varies across markets, campaigns, weekdays, and peak sales events. A single fixed threshold can create alert noise in one country while missing a meaningful change in another. I built this project to identify unusual country-level order behavior and give support teams enough context to decide what to investigate first.

Project at a glancePython and scikit-learnFour system versionsThree-model ensembleCLI, HTML, and Mattermost output

The project idea

The source data provides a country name, its expected mean hourly orders, historical standard deviation, and the latest observation. The system compares current behavior with that context, applies statistical and unsupervised ML detection, assigns an operational severity, and generates reports for human review.

The goal is AI-assisted operations—not automatic incident declaration. A flagged country may reflect a genuine service problem, a promotion, a regional event, unusual but healthy demand, or poor source data. The output therefore feeds an investigation playbook rather than taking autonomous production action.

Why use three unsupervised models?

Each model views unusual behavior differently. Isolation Forest isolates observations through random partitions. Local Outlier Factor compares local density with neighboring observations. One-Class SVM learns a boundary around expected behavior. Combining their decisions provides broader coverage than relying on one model's assumptions.

V4 keeps the behavior configurable. The documented settings use 100 Isolation Forest estimators with 0.1 contamination, 20 LOF neighbors, and an RBF One-Class SVM with nu set to 0.1. Statistical guardrails include a standard-deviation multiplier of 2.0 and a minimum-order threshold of 5.

Input and automation

The current workflow accepts a CSV file with four fields:

Name,Mean,StdDev,Last
AE,2.0,2.0,6.0

An operator can analyze a specific file or use the --latest option to select the newest available input automatically. V4 displays both anomalous and normal countries so the report preserves the full analysis context instead of showing alerts in isolation.

Turning detection into an operational workflow

The terminal output supports a quick check, while the HTML report provides detailed results and visualizations. When enabled, the Mattermost webhook posts an executive summary, complete result context, key observations, and a reference to the report.

  1. Confirm that the input is complete, fresh, and aligned to the intended hour.
  2. Review severity, Z-score, and contributing model decisions.
  3. Compare the latest value with nearby periods and historical behavior.
  4. Check deployments, payment health, promotions, and regional events.
  5. Classify the result as business behavior, telemetry error, or service issue.
  6. Use the anomaly-analysis playbook for ticket creation and escalation.

The documented examples include the United Arab Emirates and Lithuania at Medium severity. Some observations with a modest Z-score can still be selected because the ensemble decision is not based on Z-score alone. This is exactly why model-level context and human validation matter.

Lessons and next improvements

The project demonstrates that detection is only one part of a useful anomaly system. Data validation, explainable output, alert delivery, investigation guidance, and feedback are equally important. The next improvements I would prioritize are pinned dependencies, automated edge-case tests, backtesting against reviewed incidents, model-level decision explanations, drift monitoring, deduplication, and secret-managed webhook configuration.

Most importantly, I would measure confirmed incidents, false positives, missed incidents, and detection delay. Those operational outcomes—not the raw number of flagged countries—show whether the system is improving reliability.
